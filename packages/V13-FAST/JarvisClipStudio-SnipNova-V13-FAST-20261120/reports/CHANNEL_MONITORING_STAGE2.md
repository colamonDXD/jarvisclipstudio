## What was built

1. **Premiere/upcoming `waiting` state.** The creator's preflight now reads the video's `live_status` (yt-dlp value passed through the metadata normaliser; the Data API path maps `snippet.liveBroadcastContent` onto the same vocabulary). `is_upcoming`/`is_live` raises `WaitVideo` *before* any duration/billing work: the claim becomes `waiting`, `waiting_since` is stamped once, and the attempt count is untouched. Each poll settles waiting rows first via a conditional reclaim that does **not** increment attempts, so a premiere → waiting → VOD sequence produces exactly one task. **Bound: 48 hours** (`CHANNEL_MONITOR_WAITING_LIMIT_SECONDS`, floor 300s); past it the row parks with `last_error` starting `waiting_expired: still not downloadable 48 hours after it was first seen…`. Deleted-monitor sweeps also settle waiting rows now.
2. **yt-dlp fallback detector.** `fetch_channel_entries_via_ytdlp` reads the channel's `/videos` and `/streams` tabs flat (15 each, merged videos-first, deduped by video id; one tab failing is survivable). RSS stays primary: the fallback runs only when RSS raised or returned an empty list **and** the per-channel meter allows it — **at most once per hour per channel**, stamped on `channel_monitors.last_fallback_at` for every attempt, success or failure. On recovery the monitor's health note says plainly that the feed was unavailable and the fallback recovered the videos; an empty feed confirmed empty by the fallback is a clean poll with no error note. RSS failure counting is unchanged (the RSS failure still increments `consecutive_failures` even when the fallback recovers).
3. **Re-drive.** `POST /channel-monitors/videos/{video_row_id}/retry` (backend + BFF) re-drives `parked`/`skipped`/`failed` rows that have no task: fresh attempt budget of 1, then the normal creator runs, so duration/Shorts/premiere decisions still apply — a re-drive can legitimately land back in `waiting`. Already-tasked or `queued` rows return `already_tasked` with "This video already has a task — it will not be created twice." and create nothing; baseline rows explain they were only marked as seen; unknown ids return 404. The daily cap brakes automatic creation only, so an explicit press is not cap-blocked (pinned by test). Settings activity rows in parked/skipped state without a task get a **Retry** button; the watcher's answer message is shown and the list reloads.
4. **Per-channel campaign/brief defaults.** Monitors carry optional `campaign_id` / `brand_kit_id`, validated with the manual create-task route's exact shape rules and stamped by the creator onto `create_task_with_source` exactly as the manual route does: the campaign's stored brief is snapshotted and validated with `validate_content_brief(brief, source_duration=…)` against the actual video duration, and both ids are passed through. A campaign deleted after being saved fails the creation honestly (`campaign_not_found: …`), parked/retryable like any creation failure — never a silent brief-less task. Two deliberate deviations from the manual flow, both flagged in code: **(a)** campaign existence is refused at save time with **422** (not the manual route's 404), because a settings field should fail where it is typed; **(b)** the manual route's campaign `example_url` → Reference Style seam is **not** mirrored — it downloads/analyses the example per task, which for a watcher would re-analyse the same example on every upload forever; the channel's own niche default is the watcher's equivalent.

**Optional Data-API detector: DROPPED for Stage 2, deliberately.** Items 1–4 are substantial; the detector needs Luffy's `YOUTUBE_DATA_API_KEY` (plumbing already exists: `.env.example` + `Config.resolve_youtube_data_api_key()`), cannot be live-verified in this sandbox, and adds a third detection path whose only win is quota-cheap polling. The detector seam (`detector`/`fallback_detector` constructor args) is shaped so it can slot in later without touching the poll logic.
